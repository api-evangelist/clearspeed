# Screen a participant with Clearspeed and receive the result

Clearspeed is a **write-and-callback** API. There is no read operation and no polling
endpoint. You create a participant, Clearspeed runs the voice assessment, and the result
arrives on **your** webhook endpoint. Plan for that asymmetry before you write code.

## Before you start

- Get a questionnaire-scoped API key with the `participant:write` scope. The **first**
  key for a questionnaire must be generated by an Admin in the Clearspeed web app
  (Integration page → API Keys → Generate New); the full value is shown only once.
- Configure your webhook endpoint on the same questionnaire's Integration page. Without
  it you will never see a result.
- Pick your region host and use it consistently:
  - US: `https://api.us.clearspeed.com/questionnaire`
  - UK: `https://api.uk.clearspeed.com/questionnaire`
- Authenticate every request with the raw key value — **no `Bearer` prefix**:
  `Authorization: <your-api-key>`

## Step 1 — Create the participant

`POST /v1/participant`

Required: `project_uuid` (the questionnaire) and `interview_ref_num` (your own unique
reference, "IRN"). Optional: `phone_number1`, `phone_number2`, `email`, `external_ref_id`,
`language`.

Choose the IRN deliberately. It is the **only** key that ties the eventual result back to
your record — `participant_uuid` never appears in the webhook payload.

A `200` returns `participant_uuid`, `particpant_guide_link` (note the misspelling — it is
spelled that way in the contract) and `is_participant_allowed`. Deliver the guide link to
the participant; that is how they take the assessment.

Persist `participant_uuid` now. There is no GET, so this response is your only chance to
capture it, and you need it for Step 3.

## Step 2 — Receive the result on your webhook

Clearspeed POSTs `ResultWebhookRequest` to your endpoint when a result is published or
updated.

- Match on `interview_ref_num` (+ `project_uuid`). Do **not** expect `participant_uuid`.
- Read `overall_evaluation` (observed values `HR`, `LR`, `G`, `R`, `NC`, `DC`),
  `questions_risk_rating[]`, `is_admission`, `is_counter_measure`, `is_not_complete`
  and `clear`.
- `status` distinguishes a finished assessment (`Result Published`) from
  `Attempted - Incomplete`, `Attempted - Partial` and `under_review`. Only act on the
  status values your process is designed for.
- Do **not** derive `summary` from `overall_evaluation` — Clearspeed's own published
  examples contradict each other on that pairing. Treat `summary`/`summary_bgcolor` as
  presentation, and `overall_evaluation` as the decision signal.
- Return **HTTP 200**. Anything else, or a timeout, is recorded as a failure.

Two things to build for, because Clearspeed does not provide them:

1. **No signature.** There is no HMAC header. Authenticity rests on TLS plus whichever
   credential Clearspeed presents to you (a static API-key header, or an OAuth2
   client-credentials bearer token it fetches from your token URL before each delivery).
   Configure one of those and verify it on every request.
2. **No automatic retry.** Failures are retained 15 days and replayed only when an
   operator presses "Retry Webhook" in the app. Older failures are unrecoverable.
   Acknowledge fast, queue the work, and de-duplicate on `interview_ref_num` because a
   manual retry can redeliver.

## Step 3 — Write your disposition back

`PUT /v1/participant/{participant_id}` where `{participant_id}` is the
`participant_uuid` from Step 1.

Body: `outcome` (required — your own outcome code, e.g. `$10,Reviewed and Mitigated`) and
optional `outcome_ts` in **RFC 3339** (`2025-12-12T06:06:29Z`). Omit `outcome_ts` and the
server stamps current UTC.

This closes the loop so Clearspeed can measure model performance against your real
decisions.

## Error handling

Participant endpoints return a four-field envelope: `error` (one of `BAD_REQUEST`,
`UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `INTERNAL_SERVER_ERROR`), `status`, `message`,
`timestamp` (`dd-MM-yyyy HH:mm:ss`).

- **400 `Error: Duplicate IRN.`** — that reference is already assigned. This is a
  uniqueness constraint, **not** idempotency: a retried create does not return the
  original 200 body. Clearspeed publishes no `Idempotency-Key` support, so make your own
  side idempotent — record the IRN before you call, and on a duplicate look up your
  stored `participant_uuid` rather than retrying blindly.
- **401 `API key is required` / `Invalid API key`** — missing header, or the key was
  deleted (deletion takes effect immediately).
- **403 `API Key not associated with this Questionnaire`** — the key belongs to a
  different questionnaire. Keys never span questionnaires.
- **404 `Participant not found` / `Project not found`** — check the UUIDs.

No 429 and no 5xx are declared, and no rate limits are published. Back off on anything
unexpected rather than assuming a retry budget.

## What this API does not give you

No list or read operations, no result retrieval, no sandbox or test environment, no rate
limit headers, no idempotency key, no request-id header for tracing, no status page and
no deprecation policy. Build correlation, retry safety and observability on your side.
